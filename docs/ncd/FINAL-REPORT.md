# NCDSync final report

Build of `docs/ncd/PROMPT-NCDSYNC-BUILD-v2.md` (phases P0 to P11) inside MedSync, branch `feat/ncd-registry` in the
worktree `~/Desktop/medsync-ncdreg`, cut from `origin/main` 8e45d34. Nothing has been pushed, deployed or applied to a
hosted database. Migration `0093_ncd_registry.sql` is GATED and unapplied.

This report states what was built, what a test verifies, and what remains open. **The module is not complete, not
production-ready and not approved for patient data.** Every definition in it is a draft awaiting the sign-offs in
section 9, and the human gates in section 10 cannot be closed by a build.

Run mode was continuous (owner instruction: "go through all gates"); checkpoints were recorded, not stopped at. The phase
ledger is `docs/ncd/PROGRESS.md`; decisions D-01 to D-35 are in `docs/ncd/DECISIONS.md`; ADRs 0208 to 0213 (all
`proposed`) are in `docs/adr/`.

## 1. Requirements

Status rule: `verified` only where a named test that passes asserts the requirement's acceptance behaviour.
`built_unverified` means built but not asserted by a test. Where a requirement is verified but part of it is not, the
note says which part.

**51 of 51 are `verified`; none is `built_unverified` or `not_built`.** That is a statement about tests, not about
clinical fitness: several verified requirements have parts no test asserts, listed after the table, and every
definition behind them is a draft. The table was compiled by a separate subagent that read the test bodies, then
updated for the tests added after its audit; every test named passed in the final run.

## 2. Indicators

Every indicator is a pure function in `lib/ncdreg/indicators/engine.ts` over one dataset; definitions are data in
`lib/ncdreg/standard/indicators.ts`, all at version `ind-0.1.0-draft` (status draft). The golden dataset is 69
hand-designed synthetic patients (`tests/ncdreg-db/golden/`), written by a separate agent from the definitions alone,
with every expected number hand-derived and the patient ids behind it listed in `docs/ncd/INDICATORS.md`. Reporting month
2026-09, as-of 2026-09-30. "Result: equal" means `tests/ncdreg-db/golden.test.ts` asserts the engine's number (and the
patient ids behind it) equal the expectation, in the final run.

The generic family (G01 to G06) has golden expectations for the four conditions the golden dataset enables: diabetes,
hypertension, asthma and chronic kidney disease. For the other six seeded core modules (heart failure, cardiovascular
disease, COPD, sickle cell disease, epilepsy, thyroid disease) the same generic functions run, and
`tests/ncdreg-db/extensibility.test.ts` shows that a throwaway module gets the full G family with no engine change; they
have no hand-derived golden numbers of their own.

## 7. Deviations from the prompt

- **D-02** npm, not pnpm; Node 24 present (the prompt says 22).
- **D-03** the registry person is its own table `ncd_person` with encrypted identifiers and nullable link columns to
  `patient_profiles` and `provisional_patients` (never set for a synthetic person), rather than reusing the patient
  table, which holds identifiers in plaintext and has no synthetic flag.
- **D-04** a minimal day-level `ncd_appointment` instead of the repository's slot-based `appointments`.
- **Commit type** `feat(ncd)` / `docs(ncd)` with the phase in the subject: the repository's commitlint allows no `ncd`
  type.
- **D-22** a "will return" call outcome records the promised date on the call and books no appointment, so the patient
  stays overdue until a visit (the catalogue's VM expectation); C13/C14 were re-derived for it.

- **D-31** interlock 6 is stricter than §10.6: any synthetic person, not only an active demo load, blocks real-format

- **Final re-run from a clean install.** The final run started from a clean `.next` and the committed tree, but not from
  `npm ci`: the PGlite package the database lane uses is linked from a local harness, and a reinstall removes it. The
  database is empty at the start of every PGlite test file (a fresh in-memory instance per file).
- **No browser runner.** The repository has no Playwright; layout and offline behaviour are asserted on rendered HTML
  and on a fake IndexedDB, as the prompt's fallback allows (see the notes on B5 and F7).
