## Existing NCD code (not the registry)

`lib/ncd/*` and `app/doctor/encounters/[encounterId]/_components/ncd-*` are a **decision-support protocol engine for one
consultation** (ADRs 0075, 0082) behind `NCD_CLERKSHIP_LIVE`, and a separate diabetes pack is in flight on
`feat/ncd-diabetes-pack` (`lib/ncd/pack`, ADRs 0204–0207). The registry lives in its own module, **`lib/ncdreg/`**,
routes under **`app/ncd/`**, tests under **`tests/ncdreg/`**, so the condition-code search (§5.6) scans registry code only and
neither module's code edits the other.

## Conform decisions taken from this survey

- ORM Drizzle, SQL migrations, PGlite lane for engine tests, `lib/encryption.ts`, `audit_log_changes()`, `SmsSender`,
  existing design tokens and components. No parallel pattern.
- DB access mirrors `lib/emr/db.ts`: a new NOLOGIN role `medsync_ncd_app` **without** BYPASSRLS; every NCD read and write
  runs `SET LOCAL ROLE medsync_ncd_app` with transaction-local GUCs (`app.user_id`, `app.hospital_id`, `app.ncd_principal`)
  and `request.jwt.claim.sub` for the audit trigger. So both layers of §8.1 hold for writes too, not only reads.
- Feature flag per facility in the repository's env style: `NCD_REGISTRY` = `"1"` or a comma list of hospital ids (default off).
