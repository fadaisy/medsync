# ADR 0057 — Resus actions: one shared urgency-ordering across the whole surface

**Status:** Accepted — presentation/ordering artifact (2026-06-03). Extends the airway UI-rework Addendum-2 ordering to all five ABCDE steps from a single reusable function.
**Context:** Each ABCDE step panel rendered its action board as `triggered` (in engine time-criticality order) followed by `extraRecorded` — with **no state-modifier re-ranking**: a `failed` action wasn't boosted to the top, a `performed` one wasn't receded; they sat at their priority position. In a resus the _order_ actions appear is itself a priority signal — the team's eye should land on the most time-critical action first. This formalises that into **one shared ordering behaviour** every step reuses, so A/B/C/D/E read identically. **Presentation only — the engine, the findings→action mappings, the action-state lifecycle, severity, escalation-on-failure, and the record are all unchanged.**

## Decision

1. **One shared, pure ordering function** ([lib/resus/action-order.ts](../../lib/resus/action-order.ts), TDD — 9 tests). `orderResusActions` sorts by a **deterministic composite**: the **state band** first (`RESUS_ACTION_STATE_RANK`: failed 0 → indicated 1 → in_progress 2 → deferred 3 → performed 4 → not_indicated 5 — §1.2 of the kickoff), then the engine's **time-criticality** (`priority`, lower = more urgent) within the band, then **stable** (equal keys keep input order; the function does not mutate its input). An unrecorded action is treated as `indicated`; a recorded-only action (no engine priority) sorts after triggered ones in its band. So every board reads top→bottom: **must-escalate → recommended → underway → parked → done → N/A**, and colour + position reinforce the same priority (the loud colours cluster at the top).
2. **Surfacing ≠ filtering (the safety guardrail).** The function SORTS, it never removes — every action passed in comes back out (a regression test asserts this). Each panel merges `triggered` ∪ `recorded` into ONE ordered list (deduped by code; a triggered action carries its recorded state), so **no `failed`/`indicated`/`in_progress`/`deferred` action is ever hidden**. `performed`/`not_indicated` recede to the bottom via the sort (+ the existing receded styling) but stay present/auditable.
3. **A persistent outstanding-actions indicator.** `outstandingActionCount` (failed + indicated + in_progress) drives a shared "N outstanding" badge in every board header ([resus-actions-heading.tsx](../../app/nurse/resus/[episodeId]/_components/resus-actions-heading.tsx)) so nothing time-critical is missed on scroll. `mostUrgentAction` feeds an `aria-live="polite"` / `role="status"` screen-reader region that announces the current most-urgent action — so a jump-to-top on `failed` reaches non-visual users with the same priority signal. Deterministic (no motion-conveyed meaning; reduced-motion-safe).
4. **Whole-surface consistency.** The shared function + heading are applied in all five step panels (airway/breathing/circulation/disability/exposure). **No consolidated cross-step actions tab exists today**; if one is added it reuses the same function (ordering by the composite _across_ steps, step context preserved). Each panel keeps its own `ActionCard` (airway's renders a dose line the others don't — so the card itself was intentionally NOT unified; only the ordering + the heading/indicator are shared). The per-card `ActionCard`/style duplication is a known, deferred cleanup — out of scope for an ordering-only change.

## Consequences

**Positive:** the actions board reads as a priority queue (failed → recommended → underway → done) consistently across the whole resus surface from one function; failed actions surface at the top where escalation is needed; a persistent outstanding count + a live-region announcement keep pending work visible (incl. for screen-reader users); deterministic + transparent (same findings/states → same order). **Negative:** the `ActionCard`/state-style duplication across the five panels remains (deferred — the dose-line difference made a full card unification risky for an ordering-only change); a future consolidated cross-step actions tab will need to pass per-item step context (the function already supports it — it sorts whatever it's given).

## Guardrails honoured

Engine, findings→action mappings, action-state lifecycle, severity classification, escalation-on-failure, and the immutable record are **byte-for-byte unchanged** — this is a render-time sort + a shared heading. No migration touched.
