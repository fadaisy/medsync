# ADR-0077 — Lab result entry → release/reject (the lab write-side slice)

**Status:** Accepted (CSO-directed, 2026-06-17). Built on `feat/lab-result-entry-release`. Completes the lab-tech workspace started in PR #137 (worklist) + PR #138 (GATED migration 0050 + critical-value catalog). Uses the already-shipped, GATED migration 0050 columns on `encounter_results`, plus **one new GATED migration (0051)** — a unique index enforcing one result row per order (the DB backstop for the entry upsert; see decision 3).

**Context:** The lab-tech workspace had the read-only incoming worklist (orders-out → results-in) and the write-side schema/critical-value catalog shipped dark, but no way for a technologist to actually **enter, release, or reject** a result. The orders→results pipe is one shared data contract (no fork). Results are clinical data: a half-entered or unverified value must never read as final, and a critical value must never be auto-raised on an unratified threshold.

## Decision

1. **Server actions, not an Edge function** (`app/lab/actions.ts`) — mirrors the clerkship write precedent (`submitClerkshipAction` → `recordClerkshipVersion`): `"use server"` + `requireLabTechScope()` + Zod validation + the service-level Drizzle `db` + an append-only `encounterEvents` (kind `result`) audit row per act. Three actions: `enterLabResultAction`, `releaseLabResultAction`, `rejectLabResultAction`. All gated on `labResultsLive()` (`LAB_RESULTS_LIVE=1` + migration 0040); each re-verifies the order/result belongs to the tech's hospital (RLS is bypassed by the service db, so scope is enforced in code).
2. **entered ≠ released (the core invariant).** Entering sets `qualityStatus='entered'`, `releasedAt=null` — NOT visible to the clinician. Releasing is a separate, deliberate act that sets `qualityStatus='released'` + `releasedAt/By` and moves the order to `resulted`. Rejecting sets `qualityStatus='rejected'` + a required `rejectionReason` (recollect). A released result is frozen (only `entered`/`rejected` rows are re-enterable; post-release amendment is a follow-up).
3. **One result row per order (upsert of the non-released row), backed by a unique index.** `encounter_results` has no append-only trigger (unlike `clinical_documentation`), so a correction before release updates the entered row; the per-act audit lives in `encounterEvents`. This keeps the clinician read one-to-one. The select-then-upsert in `enterLabResultAction` is not atomic on the service connection, so migration **0051** adds a `unique index … (order_id)` as the DB backstop (replacing the non-unique `enc_result_order_idx`); the action catches the unique-violation and falls back to an update (a lost race degrades into a correction). Provably safe to apply: no code path inserts into `encounter_results` except this DARK action, so the table holds zero rows today. The three reads (`loadEncounterOrders` ×2 + the lab worklist) additionally collapse the orders→results join to one row per order — defence in depth so a stray duplicate can never double-render an order.
4. **Release-aware clinician read** (`loadEncounterOrders`): gated — when the workflow is live, only a **released** (or a legacy pre-workflow null-quality) result shows as final; an `entered` result reads as pending ("in lab"), a `rejected` one as recollect. When off, the legacy path selects ONLY pre-0050 columns, so it is safe un-migrated.
5. **Critical flag computed, alert deferred.** On entry the value→critical-flag is computed via the GATED `evaluateCriticalFlag` (inert until `CRITICAL_VALUES_CSO_SIGNED`) and stored. On release of a flagged result the action logs it; the `sa_notifications` fan-out to the ordering clinician needs a new notification kind (a migration) and is a documented follow-up — it can't fire until the critical list is CSO-signed regardless.
6. **No fabrication.** Every field is entered by the technologist; nothing is auto-entered; a critical is never auto-raised on an unratified threshold; pending/rejected ≠ normal.

## Consequences

- Technologists can run the full result lifecycle (enter → release/reject) on `/lab`; clinicians see only released results (W4 `InvestigationsPanel` gains pending/rejected awareness via the new optional `resultPending`/`resultRejected` fields).
- Ships **dark** behind `LAB_RESULTS_LIVE` (set to `1` only after the owner applies migrations 0050 **and** 0051 via `npm run db:migrate`). Critical-value alerting additionally waits on `CRITICAL_VALUES_CSO_SIGNED`.
- Pure validation + critical-flag derivation are unit-tested (`tests/lab/result-entry.test.ts`); the write path mirrors the audited clerkship precedent.
- **Open follow-ups:** the `sa_notifications` critical-value fan-out (+ its notification-kind migration); post-release amendment flow; a second-verifier requirement for criticals on release; the lab-assistant (non-council, attestation) cadre seed if that tier is needed.
