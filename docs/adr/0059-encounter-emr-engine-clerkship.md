# ADR 0059 — Encounter / EMR engine + structured clerkship (the clinical-data spine)

**Status:** Accepted (spine) — CLINICAL-SAFETY + PDPO-critical artifact (2026-06-04). **The migration is GATED (not applied to prod); awaiting CSO sign-off of the access model + schema + clerkship structure** before apply. GATE A design in `docs/encounter-emr-engine-gate-a-proposal.md`; clinical source `docs/clinical/clerkship-clinical-reference.md` (Hutchison's Clinical Methods 24th ed.).
**Context:** The encounter/EMR engine is MedSync's clinical-data spine. The addendum (`encounter-engine-clerkship-addendum.md`) makes the encounter's clinical documentation a **structured Hutchison CLERKSHIP** (history → examination → differential → initial management), not a free-text note, populating the engine's objects. **The primary spec `encounter-emr-engine-kickoff.md` was not provided** — the schema + access model here are **inferred** from the addendum + the existing repo primitives and are **flagged for CSO ratification** (this ADR records the build; the proposal records the open questions).

## Decision

1. **Build ON the existing `encounters` table (migration 0028), don't recreate.** Migration `0040` ALTERs it (+`disposition`, `triage_record_id`, `encounter_class`) and adds the clinical objects: `clinical_documentation` (versioned, append-only clerkship), `encounter_diagnoses`, `problem_list`, `patient_allergies` (the canonical `db/schema/prescribing.ts` object — **shared** with the gated 0039, which also declares it; 0040 creates it **idempotently** and is the **authoritative owner**, superseding 0039's hospital-scoped RLS policy with the relationship-based one), `encounter_medications`, `encounter_orders`/`encounter_results`, `encounter_events` (append-only timeline). **The migration is GATED** (header: do-not-apply-without-named-authorization) — the clinical-data spine is hard-to-reverse; same posture as 0039.
2. **Access model — legitimate relationship, least-privilege, audited** (`§B` of the proposal, INFERRED). RLS on every clinical table: readable by the **patient** (transparency), **superadmin**, or a clinician with a **legitimate relationship** — `has_clinical_relationship(patient)` = active clinical staff (`staff_affiliations` ⋈ `cadres.is_clinical=true`) at a hospital where the patient has an encounter, **OR** an unrevoked, unexpired **break-glass** grant (keyed on `sa_break_glass_grants.actor_id`/`patient_id`). **Reception (`is_clinical=false`) is excluded at the DB.** Clinical **writes go through service-role server actions only** (no client write policy); documentation + the timeline are **hard append-only** (block triggers — corrections create a new version). **⚠️ The engine's own reads/writes use the service-role client, which BYPASSES RLS** — so the relationship is **re-checked in application code** (`lib/encounter/scope.ts → hasClinicalRelationship`, mirroring the SQL) on **every** clinical read/write; RLS is necessary-but-not-sufficient for these paths. **Audit-on-READ** is enforced in the read path (`loadEncounterRecord` authorises, fetches, then writes the access event **after** a successful authorised fetch — so a denied/failed read leaves no false "record read" event; reads don't fire DB triggers).
3. **The clerkship is the documentation** (`lib/encounter/clerkship.ts`, pure, TDD). The structured Hutchison sections (history incl. SOCRATES + CAGE + systematic enquiry + Uganda always-asks + allergies; examination; synthesis incl. ranked differential with must-not-miss + problem list + justified investigations + management/disposition/safety-netting), **SOAP-mapped**, **structured-but-flexible** (every field optional; honest completeness; emergency-defer). `deriveClinicalObjects` fans the clerking out to the engine objects (no parallel store; no fabrication — blank entries dropped). `seedClerkshipFromTriage` makes the clerking a **continuation** of triage (PC + acuity + carried vitals), never a blank restart.
4. **Cadre-write rules** (`lib/encounter/access.ts`, INFERRED): a doctor/clinical-officer clerks; a **junior (intern) clerking is co-signed** (soft — diagnoses stay `working` until a senior attests); a nurse records allergies/observations but not a final medical diagnosis; reception writes nothing. Enforced in `recordClerkshipVersion`.
5. **Allergies → the prescribing check.** The clerking writes `patient_allergies` (the canonical table the prescribing allergy check is intended to read). **⚠️ HARD pre-launch dependency:** the prescribing engine **currently reads the resus-timeline allergy capture** (`lib/prescribing/administration.ts → recordedAllergiesFromTimeline`), **not** `patient_allergies`. Until it is pointed at the table, **clerked allergies silently do not gate prescribing** — so wiring the prescribing read to `patient_allergies` MUST land before this feature is turned on (tracked in Scope/deferred).
6. **Decision-support, not autonomous** — no auto-diagnosis; the clinician examines, reasons, decides. PHI free-text lives in `section_data` (encrypted at the app layer like other note bodies).

## Scope / deferred

- **Built (this spine):** the schema + GATED migration + RLS/access + append-only + audit-on-read; the pure clerkship engine (sections, SOCRATES/CAGE, SOAP, derivation, completeness, triage seeding) + cadre rules + tests; the service-role write/read/audit orchestration.
- **Deferred (next increment — flagged, NOT built):** the **clerkship documentation UI surface** (the guided history/exam/synthesis form) + record/timeline view + doctor/nurse-workspace wiring — deliberately not shipped blind because it cannot run until the gated migration is applied; it lands once the CSO ratifies the schema + applies 0040. **Launch-blocker (must precede turn-on):** point the prescribing allergy read at `patient_allergies` (see Decision §5). Also later: particular-group flows (paediatric/obstetric/older/psychiatric/emergency/fever/pain) + system-specific exam templates (Hutchison Section 2/3); order **execution** + results ingestion; the tighter care-team RLS variant; the **admission slice** (consumes the disposition).

## Consequences

**Positive:** a real, reviewable clinical-data spine — `encounters` extended, the clinical objects defined with RLS + append-only + audit-on-read, the clerkship as structured/versioned documentation that populates the objects (no parallel store), triage continuity, cadre-scoped writes — all tested at the pure-logic layer and signed-off-able as a unit; nothing is applied to prod until the CSO ratifies. **Negative:** the schema + access model are **inferred** (the primary spec wasn't provided) — they need CSO reconciliation against the real spec before apply; the UI surface is deferred (the spine can't be exercised end-to-end until the migration is applied); the access predicate ships the "any clinical staff at a hospital the patient has an encounter at" relationship (the tighter care-team+break-glass variant is the CSO's call).
