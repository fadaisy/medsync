# Lab test menu v2: GATE A proposal

Status: **signed** (see the end). The build follows this document; where it differs from the prompt, this wins.

## 1. Schema diff (migrations 0171 and 0172; ADRs 0350–0355)

**0171 `lab_test_menu_v2` (hand-written, GATED)**

- `test_catalogue` gains the TM-2 catalogue facts:
  - `section` (the eight keys), `aliases text[]`;
  - `specimen`, `tube`: the Ugandan wording. `specimen_type` and `container` stay as they are, because they are
    enum keys the labels and the order sheet read;
  - `order_loinc`, `min_level`, `level_basis jsonb`, `usual_route`;
  - `refer_to`: CPHL, NTRL, UVRI, UBTS, UCI, private, and `MAK_PATH` (TM-D11);
  - `kit_dependent_ranges`, `advisory`, `offer_by_default`.
- `diagnostic_offerings` is re-keyed by test id (TM-3). Lab rows use `code = test_catalogue.code`. It gains:
  - `section_override` (the eight keys);
  - `stated_turnaround_minutes`. `stated_tat` stays as the words the ordering contract reads; the menu writes both.

  No new offering table (DX-1: one store). `section_id` stays only for legacy rows that are not in the catalogue (LW-3).

- `lab_settings.hidden_sections text[]` (TM-5).
- `lab_order_profiles` (TM-10):
  - columns: hospital, name, note, `test_codes text[]` in order, active, audit columns, `client_key`;
  - the test list is an array, not a second table. Order matters and the list is short.
- `lab_catalogue_requests` (TM-11):
  - columns: hospital, requester, name, purpose, specimen, route, reference, state, reason, `test_code`, decider,
    `client_key`;
  - check constraint: a decline needs a reason; `added` needs a test code.
- Every new table:
  - RLS on and forced;
  - `audit_log_changes` on every row change (TM-13: one audit row per test in a bulk action);
  - INSERT, UPDATE and DELETE revoked from `anon` and `authenticated`;
  - writes go through server actions, which check permissions in the app (as `lab_test_services` does);
  - reads: offerings and profiles by the hospital's staff, its admin and superadmin; requests by the requester's
    hospital and superadmin.

## 2. Migration of per-LOINC settings (TM-9)

- `planOfferingMigration` is pure, in `lib/lab/test-menu.ts`. `scripts/lab/migrate-offerings.ts` runs it:
  - `--dry-run` (the default) writes `migration-report.md`;
  - `--apply` writes the test rows. The owner runs it after 0171 and 0172.
- A LOINC row maps to every catalogue test whose components carry that code. The codes come from the registry,
  the v1 research and catalogue v2.
- A test inherits where, hours and stated turnaround when all of its set components agree. Otherwise it takes the
  most common value and is listed (TM-D10).
- A section that differs from the catalogue's becomes `section_override`. Unmapped rows are listed.
  Existing test rows are never overwritten.
- Test Hospital-1 dry run (from the capture): 30 rows become 27 tests, with 0 conflicts. 2 rows are unmapped:
  `69419-0` (LDL direct, carried by no catalogue v2 test) and `DEMO-REF-TFT` (the demo's non-LOINC row). The
  prompt expected about 8. Shared analytes are the cause: albumin and glucose each sit in 5 tests, creatinine in 3.
  The report shows each test's coverage, so the owner can set unwanted ones to Not offered after applying.
- Orders are never touched: they keep their `loinc_code` and availability snapshot (S18).

## 3. Screens (boards 13–18), one component, two entry points

- `components/lab/test-menu/` holds the screens. Lab: `/lab/setup/menu` (tabs Test menu · Hospital profiles ·
  Test catalogue · Analyser profiles). Hub: `/hospital-admin/departments/diagnostics` (Laboratory).
- **Board 13 (Test menu):**
  - summary strip;
  - section and Where lists;
  - grouped table with "Set hours for the section";
  - the results chip line;
  - Where segmented control;
  - availability ink or amber pill;
  - search and filter chips;
  - navy bulk bar.

  A row opens Test detail.

- **Board 14:** level cards → section ticks → hours choice → the preview when the menu is not empty → "Add {n} tests".
- **Board 15:** search across the catalogue, section chips, "Often ordered with these", and Add / On your menu /
  Not yet signed.
- **Board 16:** editable fields on the left and catalogue facts on the right. Remove sets Not offered after showing
  the consequence.
- **Board 17:** profile cards plus New profile.
- **Board 18 (why):** the docs and the ADR.
- Pop-ups are centred `EditorDialog`s. Red only for Emergency; nothing green. Changed sections are ink text.
  Advisories are ink text with an info icon.

## 4. Template rules (TM-6, signed by TM-D03 to TM-D05)

- Skip `offer_by_default = false`.
- **In-house** when level(min) ≤ L and (basis is the 2017 national menu, or `usual_route = in_house`, or L ≥ NRH).
- **Referred** when level(min) ≤ L+1, or `refer_to` is CPHL, NTRL, UVRI or UBTS. National `refer_to` becomes
  `referred_to`.
- Hours: 24 h, Working hours, or Set later. Stated turnaround is never filled.
- Snapshot: HC III 33/69 · HC IV 61/83 · GH 110/69 · RRH 151/64 · NRH 197/88.
- "Private laboratory" has no template of its own: choose the nearest level.

## 5. Profiles and requests

- **Profiles (TM-10):**
  - the lead or the admin creates one from tests on the menu that are offered;
  - a name naming a restricted condition is refused;
  - on the order sheet a profile adds one line per test;
  - removing a test from the menu flags its profiles.
- **Requests (TM-11):**
  - the requester fills the short form; hospital-number patterns are refused;
  - the superadmin queue at `/admin/lab-catalogue-requests` moves a request through in review, added (with the
    catalogue test id, after a signed addendum) or declined (with a reason);
  - the requester sees the state and reason in the list under the form.

## 6. Who sees restricted names

- The laboratory lead sees them.
- The hospital admin and every non-lab viewer see "Restricted test" with the section. Masking happens in the read:
  masked rows carry no name, aliases or results, so search cannot find them.
