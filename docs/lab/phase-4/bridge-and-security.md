### 1.6 Recommendation

**Option A: adopt the OpenELIS Analyzer Bridge unmodified (image pinned by digest), with a MedSync companion on the
same PC for authentication and heartbeat, and a server adapter for its contract v1 bundle.**

Reasons:

1. It already meets the parts where a mistake loses or doubles a result (AB-3, AB-5, the outbox).
2. Unmodified means no MPL publication duty beyond pointing to upstream source.
3. Its auth does not fit Vercel; the companion fixes that without touching its code, and is the same JWT client
   partners use (§2), so there is one machine-auth scheme in MedSync.
4. MedSync accepts its FHIR shape at the edge only: the adapter turns the bundle into one `exchange_messages` row
   (`channel = 'fhir'`, `external_id = Bundle.identifier`), then the normal MA-2 path. Its LOINC hints are dropped.

What adopting means we accept, said plainly:

- **Its output shape.** We depend on `analyzer-normalized-bundle-v1`. A contract v2 means adapter work.
- **Its management model.** Connections and profiles are set on site, through its localhost API, by a person with
  access to the PC. MedSync cannot push them. The companion reports the pinned profile id and revision in each
  heartbeat; Analysers shows it, and a revision the lab lead has not signed is an amber note.
- **Its storage.** Plain SQLite. Encryption at rest comes from the host's full-disk encryption (§2.9).
- **Its speed of change.** Twelve releases in five weeks. Upgrades are a GATE S item, never automatic
  (`pull_policy: always` in its compose file must be removed).

**Owner decision needed (D-LAB4-14):** A as recommended, or C. If the maker's document shows an analyser the bridge
cannot drive (e.g. a transport or framing it lacks), Step 10 reopens this as C.

## 2. D-LAB4-15 and the GATE S security design

### 2.1 Decision

**Signed JWT client assertion (SMART Backend Services pattern) for every machine, bridge or partner.** Mutual TLS is
not possible on this hosting without a proxy (STOP 0 item 7; §1.2 AB-6). This changes the prompt's recommendation
(mTLS first), as `gate-a-proposal.md` P6 already records.

SMART facts used (read 17 Oct 2026, SMART App Launch 2.2.0, STU 2.2, FHIR R4):

- Token request: POST, form-encoded, `grant_type=client_credentials`,
  `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, `client_assertion`, `scope`.
  TLS 1.2 or later. Response: `access_token`, `token_type=bearer`, `expires_in`, `scope`. `expires_in` "SHOULD NOT
  exceed 300". "Refresh tokens SHOULD NOT be issued." `system/` scopes. https://hl7.org/fhir/smart-app-launch/backend-services.html
- Assertion: header `alg`, `kid` (unique in the client's key set), `typ=JWT`, optional `jku`. Claims `iss` = `sub` =
  client id, `aud` = the token URL, `exp` no more than five minutes ahead, `jti` unique. Clients SHALL support
  **RS384 and ES384**; servers validate at least one. Server rejects a reused `jti` for the same `iss` within the
  lifetime; picks exactly one key by `kid` and key type; any failure → `invalid_client`. Keys registered as a JWK
  Set by URL ("strongly preferred") or by value ("strongly discouraged").
  https://hl7.org/fhir/smart-app-launch/client-confidential-asymmetric.html
- IHE ITI-19 (Rev 20.0, 4 Aug 2023): mutual X.509 node authentication, TLS 1.2+ per BCP195, certificates at most
  2 years, authorisation by CA chain "strongly discouraged". It names TLS, not OAuth. We meet its intent (both ends
  authenticated, local trust, not CA-based authorisation), not its letter. https://profiles.ihe.net/ITI/TF/Volume2/ITI-19.html

**Where we differ from SMART, on purpose:**

| Point            | SMART                                        | Ours                                                                                                                                                                              | Why                                                                               |
| ---------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Key registration | JWK Set URL preferred                        | **By value**, at pairing                                                                                                                                                          | The device hosts nothing on the internet (AB-1). Rotation is by re-pairing (§2.6) |
| Scopes           | Resource scopes, e.g. `system/Observation.c` | `system/exchange.inbound.write`, `system/exchange.config.read`, `system/exchange.heartbeat.write`                                                                                 | Our endpoints are not a FHIR REST server. SMART-shaped, not SMART resource scopes |
| Algorithms       | RS384 and ES384                              | **Allowlist ES384 and RS384.** The brief said ES256/RS384; ES256 is not in SMART's required pair. Recommend ES384 for our companion; add ES256 only if a partner cannot do either | Owner decision at GATE S                                                          |
| `jku`            | Allowed if it matches the registered URL     | **Rejected** if present (no URL registered); `jwk`, `x5u`, `x5c` headers also rejected                                                                                            | No remote key fetching                                                            |

### 2.4 Tokens

**Token endpoint** `POST /api/exchange/token`, checks in this order; any failure answers 401 `invalid_client` with the
same body (no hint which check failed), and is counted and audited:

1. Form fields exact; `grant_type`, `client_assertion_type` as SMART says.
2. JWT header: `typ = JWT`; `alg` in the allowlist (ES384, RS384); `kid` present; no `jku`, `jwk`, `x5u`, `x5c`.
   `alg = none` and HMAC algorithms refused by the allowlist.
3. `iss = sub` = a known sender in `state = 'active'`, not revoked.
4. Exactly one key in that sender's `jwks` with that `kid` and a key type that fits `alg`.
5. Signature checked with `node:crypto` (`createPublicKey({ key: jwk, format: 'jwk' })`, `verify('sha384', …)`;
   EC signatures in JOSE form, `dsaEncoding: 'ieee-p1363'`).
6. `aud` equals the token URL exactly.
7. `exp` present, in the future (clock-skew allowance **set at GATE S**, operational), and no more than 300 s ahead.
   `iat`, if present, not in the future beyond the allowance. `exp − iat` ≤ 300 s when both are present.
8. `jti` inserted into `exchange_jti` with `expires_at = exp`. A unique-key clash means replay: refused. Rows past
   `expires_at` may be deleted (operational, not clinical).
9. Requested scopes ⊆ the sender's scopes; grant the intersection.

Then issue an **opaque** token: 32 random bytes, base64url. Store only its SHA-256 with sender, hospital, scopes and
`expires_at` (≤ 300 s). Answer `{ access_token, token_type: "bearer", expires_in, scope }`. **No refresh token.**
The server holds **no signing key**: opaque tokens need none.

> Gap for `gate-a-proposal.md` §3.4: an opaque token needs a small table, e.g.
> `exchange_tokens (token_sha256 text PRIMARY KEY, sender_id uuid, scopes text[], expires_at timestamptz)`.
> §5.3 step 1 there reads as if the inbound route checks the client assertion itself; with a token endpoint it
> checks the access token. Either works; one must be chosen. Recommended: token endpoint (SMART, as briefed).

**Inbound endpoint** `POST /api/exchange/inbound/{hospital}/{sender}`, before anything is stored:

1. `Authorization: Bearer …` → SHA-256 → token row exists and `expires_at > now`.
2. The sender row is still `active` (this is what makes revocation immediate, §2.5).
3. Scope includes `system/exchange.inbound.write`; URL hospital and sender equal the token's.
4. Size cap; Zod envelope; then EX-2 (store, commit, `202 { messageId, duplicate }`).

Config read and heartbeat check the same way with their own scope. `proxy.ts` does not gate `/api/*` beyond its public
list, so these routes do their own auth; consider excluding `/api/exchange` from the proxy matcher so no session work
runs for machines.

Note for the companion: the bridge dead-letters any 4xx, including 401. The companion must fetch a new token and
retry **before** answering the bridge, and answer 503 (retry) on its own token failures, never 401.

### 2.5 Revocation at once

`revokeBridge` (and `disableConnection` for a partner) by the laboratory lead (AAL2, fresh second factor, reason,
audited): sender `state = 'revoked'`, `revoked_at` set, its token rows deleted. Because step 2 of every check reads
the sender state, the next request fails, **within seconds, not five minutes**. Messages already held stay (Law 6).
A revoked sender can only come back by pairing again with a new key.

### 2.6 Key rotation

- **Routine:** re-pair. The lab lead makes a new code; the companion makes a new key pair and pairs; the server
  replaces `jwks` once the new key is confirmed (§2.3 step 6); the old key stops working then. Interval **set at
  GATE S** (ITI-19's two-year certificate ceiling is a reasonable upper bound).
- **On suspicion** (theft, PC rebuilt, staff leaving with access): revoke first (§2.5), re-pair second.
- No in-band rotation in this slice. Add it only if re-pairing proves a burden.

### 2.8 Outbound only

- The bridge PC opens no port to the internet. No port forwarding, no tunnel.
- Egress from the PC: 443 to the MedSync host only (firewall allowlist), plus OS updates.
- Bridge port 8443 bound to `127.0.0.1` (compose: `127.0.0.1:8442:8443`). Analyser ports (12001, 12011, 2575 as the
  profile needs) bound to the lab-side interface and firewalled to the analyser's address. Do not use the bridge's
  HTTP `/input` transport (it would need 8443 on the LAN).
- Set `BRIDGE_PAIRING_CODE` to a long random value nobody uses, so the bridge never logs a usable code and is never
  paired by anyone. Keep `bridge.security.password` set (Basic stays the localhost credential).
- The companion listens on `127.0.0.1` only.

### 2.9 Threats

**An attacker on the lab network can:**

| Can                                                                                                                                                                | Limit                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Send forged ASTM or HL7 to the analyser port (those transports have no authentication; the bridge attributes by address, which can be spoofed on the same segment) | A forged result lands **preliminary**, must pass MA-2 (received specimen, signed code map, matching unit, not released), and a technologist releases it under the QC hold. During shadow run it is compared, not filed. Control: analyser on its own cable or VLAN; host firewall to the analyser's address |
| Read analyser traffic (ASTM/HL7 are plain text: sample ids, results, sometimes names)                                                                              | Physical and VLAN separation only; analysers do not do TLS                                                                                                                                                                                                                                                  |
| Stop the bridge working (flood, unplug)                                                                                                                            | AB-13: "Not heard since"; Phase 1 downtime entry                                                                                                                                                                                                                                                            |

**An attacker on the lab network cannot:**

- reach the bridge's admin API or the companion (localhost only);
- act as the bridge towards MedSync without the device's private key;
- read anything from MedSync: the machine scopes include no read of PHI, messages or other senders;
- change a code or unit mapping (server-side, signed by the lab lead);
- write for another hospital (sender bound to one hospital in the token);
- replay a captured assertion (`jti`, ≤ 5 min) or a token beyond 5 minutes (and only on TLS, which they cannot read).

**A stolen bridge disk (E-LAB4-03) exposes, unless controlled:**

| On the disk                                                                                                          | Exposure                                                | Control                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `outbox.db`: raw messages and rendered bundles (sample ids, results, patient id and name if the analyser sends them) | Plain SQLite. Delivered entries kept forever by default | **Full-disk encryption** (LUKS on Linux, BitLocker on Windows). Set `bridge.outbox.retention.delivered` to the window **set at GATE S** (pruned only after MedSync confirmed delivery, which E-LAB4-03 allows). Undismissed dead letters are never purged (Law 6). Set `bridge.outbox.payload-access-enabled=false` |
| The companion's private key                                                                                          | Can post as the bridge until revoked                    | Revoke at once on any loss (§2.5); disk encryption; file readable by the companion's user only                                                                                                                                                                                                                      |
| The bridge's own TLS key (it makes one)                                                                              | Unused in option A                                      | None needed                                                                                                                                                                                                                                                                                                         |

**Full-disk-encryption trade-off for the owner:** TPM-only unlock lets the PC restart unattended after a power cut
(common), but a whole stolen PC still boots to a login prompt. TPM plus PIN protects better but stops results flowing
after every power cut until someone types the PIN (the analyser keeps its own results meanwhile). **Decide at GATE S.**
