# Lab Phase 4 research notes: referral, results return, national exchange, analyser interfaces

Compiled 13 Oct 2026 for `PROMPT-LAB-PHASE-4.md`. Two parts, each with its own sources and confidence marks (H = primary source read directly; M = secondary or partial; L = inferred or weak). Re-verify at build time; several national systems changed in 2026.

- **Part A** — Uganda: the National Sample Transport and Results Network, IRRDS and ResTrack, how results come back (paper, VL dashboard, LabRDS, LabXpert), A-LIS, the national Laboratory Data Repository, HIE and registries, the Data Protection and Privacy Act 2019, VHF specimens.
- **Part B** — Standards and analysers: CLSI LIS01/LIS02 (ASTM), HL7 v2 and IHE LAW, LIVD, the Dymind DH-615, Mindray BS-240, Roche cobas c 111 and HumaStar 600, the OpenELIS Analyzer Bridge pattern, FHIR R4 Task and OpenHIE lab workflows, barcodes, patient matching.

**Headline for the build:** no national system (IRRDS, ResTrack, A-LIS, LDR) publishes an interface specification. Electronic national exchange needs NHLDS onboarding and a data-sharing agreement; until then paper and typed entry remain the path. Analyser interfacing needs each maker's LIS document for the exact model on site.

Research date: 13 Oct 2026. Every item below has a source link and the place in the source where the fact appears. The confidence mark means:

**Low-level protocol (E1381/LIS01).** Details come from the vendor LIS spec _Beckman Coulter UniCel DxI / Access 2 LIS Vendor Information_, C03112-AF, May 2026: https://www.beckmancoulter.com/download/file/wsr-228138/C03112AE?type=pdf. **H** for that vendor's implementation, **M** as a statement of the standard.

- **Phases:** establishment, transfer, termination.
- **Establishment:** sender sends `ENQ`. Receiver answers `ACK` (ready) or `NAK` (busy; sender retries after 10 s). If both sides send `ENQ` at once (contention), the instrument wins: the host goes neutral and waits up to 20 s.
- **Frame format:** `STX FN text ETB|ETX C1 C2 CR LF`.
  - FN is the frame number, 0–7 modulo 8. The first frame is 1.
  - A frame is at most 247 characters including 7 overhead characters, so 240 data characters.
  - Longer records are split. Intermediate frames end with `ETB`; the last frame ends with `ETX`.
- **Checksum:** sum of the bytes from FN through ETB/ETX, mod 256, sent as 2 uppercase hex ASCII characters.
- **Receiver replies:**
  - `ACK`: frame accepted.
  - `NAK`: frame rejected; the sender resends the same FN.
  - `EOT` in reply to a frame: frame accepted, and the receiver asks the sender to stop.
  - After **6 failed attempts** on one frame the sender aborts and must later resend the whole message.
- **Timeouts:** 15 s (no reply to ENQ or to a frame); 30 s (receiver waiting for a frame).
- **Termination:** sender sends `EOT`; no reply.

**Record layer (E1394/LIS02).** Same Beckman doc.

- **Record types:** H (header), P (patient), O (order), R (result), C (comment), Q (request information / host query), L (terminator). M (manufacturer) and S (scientific) also exist; Beckman ignores them.
- **Delimiters:** `| \ ^ &` (field, repeat, component, escape). Every message runs H … L.
- **Host query (bidirectional):** when a rack loads, the analyser sends a **Q** record, e.g. `Q|1|^Samp45||ALL||||||||O`. The host answers with H-P-O-L, or with H-L if it has no orders. Q records go **analyser→host only**. Conf: **H** for Beckman.
- The HumaStar 600 uses the same pattern: Q → host replies P+O → analyser later sends P/O/R/L. It runs over RS-232. https://github-wiki-see.page/m/hmislk/hmis/wiki/HumaStar-600-%E2%80%90-Summary — **M** (wiki mirror of an open-source HMIS project).

**Field gotchas (Medplum ASTM channel docs, https://www.medplum.com/docs/agent/astm-channels — H):**

- Firmware differs in how it packs frames.
- If a bridge never sends `NAK`, it cannot trigger checksum-driven retransmits. In that case validation has to happen downstream.
- Serial analysers need a serial-to-TCP adapter for TCP-only bridges.

## 2. HL7 v2 for analysers and lab exchange; IHE LAW / LTW; LIVD

**Message types**

- **ORU^R01**: unsolicited observation (results). **OUL**: unsolicited lab observation. **OML**: lab order. **ORL**: lab order acknowledgement. **QBP/RSP**: query by parameter / response. **ORM**: label "Pharmacy/treatment order" in v2 table 0076. Source: HL7 Terminology, https://terminology.hl7.org/7.0.0/ValueSet-v2-0076.html — H.
- **OML^O21** (lab order) is used where specimen/container information sits inside the ORC/OBR group. **O39** covers whole specimen shipments. https://hl7.eu/refactored/msgOML_O21.html — H.
- The OMG/OML lab-automation messages arrived in **v2.4**. https://hl7.org.au/archive/hl7v2wg/5-Observation-Ordering_1278282.html — H.
- **ORM^O01 status:** InterSystems says "as of version 2.5 you should use specific messages… OMG, OML…". https://community.intersystems.com/print/530296 — **M**. The exact deprecation or withdrawal version in the HL7 standard was **not verified** (gap). Older analyser and HIS interfaces still use ORM^O01.

**Acknowledgement and transport (MLLP)**

- **MLLP framing:** `0x0B` + message + `0x1C 0x0D`.
- **MSA-1 codes:** AA, AE, AR (application level); CA, CE, CR (commit level, enhanced mode).
- MSA-2 echoes the original **MSH-10**. MSH-10 must be unique per sender.
- Source: https://hl7v2.hexdocs.pm/encoding-rules.html — M.
- An accept ACK means the receiver committed the message to safe storage, so the sender may stop resending. HL7 Australia **requires enhanced mode**. https://hl7.org.au/archive/hl7v2wg/8-Acknowledgement_31588902.html — H.

**IHE LAW (Laboratory Analytical Workflow)**

- **Actors:** Analyzer Manager (LIS, LAS or middleware) ↔ Analyzer.
- **Base standard:** HL7 **v2.5.1**, with some v2.8/2.9 features pre-adopted.
- **Coding:** LOINC for observation IDs, UCUM for units. JLAC10 is also named.

| Transaction                         | Request message | Response / ACK                               |
| ----------------------------------- | --------------- | -------------------------------------------- |
| LAB-27 Query for AWOS               | QBP^Q11         | RSP^K11; the actual orders follow via LAB-28 |
| LAB-28 AWOS Broadcast               | OML^O33         | ORL^O34                                      |
| LAB-29 AWOS Status Change (results) | OUL^R22         | ACK^R22                                      |

- **Acknowledgement:** LAW uses **enhanced acknowledgement** (MSH-15 = ER, MSH-16 = AL), so exactly one ACK comes back per message. Transport is MLLP (appendix B.6, not read in full). Source: 2012 LAW supplement, https://ihe.net/Technical_Framework/upload/IHE_LAB_Suppl_LAW_Rev1-2_TI_2012-10-02.pdf — M (partial read).
- **Status:** the IHE wiki still shows the profile as "Trial Implementation", but the LAB-27/28/29 transactions appear in the PaLM TF Final Text above. https://wiki.ihe.net/index.php/Laboratory_Analytical_Workflow_Profile — H.
- **Industry backing:** developed by the IICC. CDC CLIAC handout: "being implemented by all major IVD companies"; free to implement; basis for CLSI AUTO16; selected by the EU for its eHealth interoperability framework. https://www.cdc.gov/cliac/docs/addenda/cliac0418/15a_IICC_LAW_and_LIVD_Handout.pdf (2018) — H for the claim, but it is dated.

**IHE LTW (Laboratory Testing Workflow, order placer ↔ lab)**

- LAB-1 Placer Order Management uses **OML^O21**. LAB-3 Order Results Management uses **ORU^R01**. Both are HL7 v2.5.1.
- Source: https://hl7v2.hexdocs.pm/HL7v2.Profiles.IHE.LTW.html — **M** (library documentation, not the IHE text). LAB-2, LAB-4 and LAB-5 were not verified.

**LIVD (LOINC for IVD)**

- Purpose: an industry format in which IVD vendors publish suggested LOINC codes for their assays, keyed by the **vendor transmission code**. An LIS or middleware "device configurator" can ingest it directly to map analyser codes to LOINC.

## 4. Middleware / on-site bridge patterns

**OpenELIS Global Analyzer Bridge** (formerly "ASTM-HTTP Bridge"). Repo https://github.com/DIGI-UW/openelis-analyzer-bridge (the old URL https://github.com/DIGI-UW/astm-http-bridge resolves there). MPL-2.0. Docker image `itechuw/astm-http-bridge`. Conf: **H** (README read via fetch).

_Inputs and outputs_

- **Inputs:** ASTM over TCP (LIS1-A on port 12001; E1381-95 on 12011), HL7/MLLP on 2575 (optional), RS-232 serial, watched files, HTTP `POST /input`.
- **Output:** normalised results sent as **FHIR JSON** (`application/fhir+json`) to `{OpenELIS}/analyzer/fhir`.
- **Reverse direction:** OpenELIS sends LOINC-coded orders to `POST /api/orders`, and the bridge emits HL7 ORM or ASTM.

_Store-and-forward (key pattern)_

- Each valid ASTM frame is committed to SQLite (`synchronous=FULL`) **before** the ACK is sent.
- An `ENQ` ACK only opens a session; it confirms no clinical data.
- A transmission without its EOT is held as incomplete, and the analyser must resend.
- Serial HL7 commits the message before sending `MSA|AA`.
- **The bridge's ACK means "the bridge holds it", not "the LIS accepted it".**

_Outbox state machine_

- States: RECEIVED → PENDING → RETRYING (exponential backoff) → DELIVERED, or **DMQ** (dead-message queue that needs a person).
- Default retry: 150 attempts, 5 s base delay, ×2.0 multiplier, 10 min cap, 0.2 jitter.
- Operators review dead letters at `/admin/outbox`.
- Delivered raw messages are kept as the audit copy. Undismissed dead letters are never purged.
- A corrupt database is renamed aside and preserved as incident evidence.

_Duplicate detection_

- Each delivery's identity is a **content-derived hash**, and the LIS de-duplicates on it. Redelivery after a restart or an operator retry therefore does not double-file.
- An identical retransmitted ASTM frame is ACKed but not stored twice.

_Clock handling_

- Result time = ASTM R.13 (completed); if that is unreadable, R.12 (started).
- ASTM timestamps carry no UTC offset, so they are read in the container's `TZ` (default UTC). **Set TZ to the site zone.**
- With no readable time, the import time is used. HL7 and file inputs do not carry the analyser test time.

_Security_

- One-time **pairing code**; pairing locks after 10 bad attempts.
- After pairing: **mutual TLS** with **SHA-256 certificate pinning** in both directions, on HTTPS 8443.
- HTTP Basic works only until pairing. The default password blocks startup in production.
- Unpaired callers can reach only health, pairing and input.
- Durable state (outbox, identity keys) lives on a persistent volume.

**Medplum Agent** (ASTM channel). An on-premise agent listens on TCP, frames ENQ…EOT into one message, auto-ACKs at byte level, and forwards it to a server-side Bot. Weakness: it does not verify checksums or send NAK. https://www.medplum.com/docs/agent/astm-channels — H.

**Generic security references**

- **IHE ATNA / ITI-19 Authenticate Node:** mutual X.509 authentication on every HL7/HTTP connection. TLS 1.2+ per BCP195, AES-GCM suites, 2-year certificate expiry recommended. Do **not** rely on external CA chains for authorisation; use pinned or locally configured trust. https://profiles.ihe.net/ITI/TF/Volume2/ITI-19.html — H.
- **SMART Backend Services (App Launch 2.2.0):** the client-credentials grant with an **asymmetric signed JWT** assertion fits an on-prem connector authenticating to the cloud. Uses `system/` scopes (least privilege, e.g. `system/Observation.c`). Access tokens should last ≤300 s with no refresh tokens. TLS 1.2+. https://hl7.org/fhir/smart-app-launch/backend-services.html — H.
- **OpenHIE:** assumes the interoperability layer provides node authentication, audit, and re-running of failed transactions (report-results page below) — H.

## 5. FHIR lab workflow (orders, results, referrals)

**FHIR R4 Task.status** (12 codes): draft, requested, received, accepted, rejected, ready, cancelled, in-progress, on-hold, failed, completed, entered-in-error.

- `received` = performer has claimed the task and is deciding.
- `rejected` = declined before any action.
- `businessStatus` carries site-specific states such as "Specimen collected".
- Source: https://hl7.org/fhir/R4/valueset-task-status.html and https://hl7.org/fhir/R4/task.html — H.
- Task links: `basedOn` = the authorising ServiceRequest; `focus` = the request being fulfilled; `input` = Specimen; `output` = DiagnosticReport; `owner` = performing organisation (the filler).

**FHIR Workflow Management** (https://hl7.org/fhir/R4/workflow-management.html — H)

- Option G: the placer POSTs a Task to the filler's system. Option H: the Task goes through a broker. Option I: the filler creates a sub-Task.
- The filler marks acceptance, updates progress, then sets `completed` and points the Task to the result.
- The **placer** cancels; the filler decides whether cancellation is still possible.

**OpenHIE Laboratory Workflows** ("Newly Defined", ARB-approved). Sources: https://guides.ohie.org/arch-spec/introduction/laboratory-work-flows/order-laboratory-test and …/report-lab-results — H.

- **Order:** the EMR creates a **FHIR R4 Task** (alternative: a ServiceRequest) in a Bundle with Patient, and sends it to the IOL, which routes it to the SHR and the LIS. The LIS sets Task to **accepted or rejected** and creates its own ServiceRequest. Orders are matched on **LOINC**. The status update goes back via the IOL to the EMR.
- **Results:** the LIS creates DiagnosticReport → Observations, referencing Patient and Task. The EMR **polls for its Tasks with status `completed`**, then fetches the DiagnosticReports.

**Suggested referral status mapping for MedSync** (my synthesis from the sources above; conf M):

| Step                                          | Task.status                                        |
| --------------------------------------------- | -------------------------------------------------- |
| Referral sent                                 | requested                                          |
| Lab picks it up                               | received                                           |
| Lab agrees to do it                           | accepted, or rejected + statusReason               |
| Specimen arrives and testing starts           | in-progress (businessStatus = "specimen received") |
| Paused                                        | on-hold                                            |
| Result issued                                 | completed, with output → DiagnosticReport          |
| Could not run (e.g. haemolysed, insufficient) | failed                                             |
| Withdrawn by placer                           | cancelled                                          |

  - Send LOINC codes with results (1.1).
- **Counter-example:** Health Gorilla auto-files to one record when **several** match and auto-creates a patient when demographics are complete. Only incomplete or unresolvable results go to an "Unassigned Queue". MedSync should **not** copy this. https://developer.healthgorilla.com/docs/result-routing-and-matching — H.

**Recommended MedSync rule** (synthesis; conf M)

- Auto-file only when the accession/specimen ID (barcode) maps to a known order **and** at least one more patient identifier (MRN, or name + DOB) agrees.
- Anything else goes to a **reconciliation queue**: no auto-create, no "best guess" filing, with the reason recorded and a human resolving it. Every resolution is audited.
- Analyser results key on the **specimen/accession ID**, not on demographics, because analysers often carry little or no patient data.
